DNA codes · October 30, 2026

A DNA code 2.5× larger, in five hours

DNA data storage needs a dictionary of sequences that can never be mistaken for one another; the bigger the dictionary, the more information it can encode. Under the construction rules of Wang, Liu and Chen (2024), the paper's dictionary holds 676 sequences. In five hours and US$1.34 of API spend, Object Run grew it to 1,688.

Background

DNA storage writes digital information as sequences of bases. During reading and writing, sequences can hybridize with each other in unintended ways, so the sequences in use must differ from one another by enough and must not fold onto themselves. A set of sequences that satisfies these constraints is called a DNA code. With the constraints fixed, a larger set means more sequences available to tell pieces of information apart.

Our setting comes from Table 4 of arXiv:2409.06519: sequences of length 10, each with exactly 5 G or C bases; any two sequences differ in at least 4 positions; no sequence contains a pair of 3-base fragments that are reverse complements of each other; and the whole set is closed under reversal and complementation. The paper uses a [10,6,4] linear code over GF(4) to select 676 sequences, which is the reference value for this experiment.

Setup

The model received the rules above, the reference set and a sandbox with no network access. The acceptance criterion was fixed before the run and enforced by a verifier outside the sandbox, which the model could neither read nor modify. The model chose its own search methods and code; only sets confirmed valid by the verifier count toward the result. The initial target was to beat 676; each time it was reached, the target was raised to the current best within the same five-hour limit.

Results

At minute 8, the first valid set already held 1,396 sequences, twice the paper's reference set. The model grouped each sequence with its reverse, complement and reverse complement into a single orbit, built a conflict graph between orbits, reduced the problem to maximum independent set, and solved it with multi-start local search. Over the next four and a half hours it kept improving its own code. It even noticed that its own Hamming-distance prefilter was stricter than the constraint itself and corrected it, reopening the search space. The final result is 1,688 sequences, 1,012 more than the reference set.

Verification

The final set is stored in plain text, one sequence per line. Two independently written verifiers check every constraint pair by pair with exact integer arithmetic, and they agree: the minimum Hamming distance is 4, and the GC content, fragment exclusion and closure conditions all hold. SHA-256 hashes of the set file and both verifiers are recorded for reproduction.

Notes

The paper's text also describes a stronger reverse / reverse-complement distance condition that the paper's own published set does not satisfy. This experiment uses the rules the paper's actual construction satisfies, so the result is compared with the reference set on the same terms. The run made 364 model requests, with 41.66 million input tokens (33.13 million served from cache) and 1.13 million output tokens.
